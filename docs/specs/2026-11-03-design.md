# orca-box design (2026-11-03)

## Goal

One dedicated home box runs the Orca server. Agents (Claude Code, Codex, GitHub Copilot CLI) do development work there on any project, and they keep working while the owner's computer sleeps or travels. The box becomes the main development machine. The owner's computer, phone and tablet are the ways to give it work.

The box must be able to finish work on its own, including merging and deploying to staging.

This repo is the procedure to **set up, watch, destroy and rebuild** the box. Each should be short and repeatable.

## Security stance

Agents run unattended with permission prompts off, so prompt injection is always possible. Assume the box, host included, can be taken over at any time. The hardware is not precious, and not every attack can be prevented. The design aims at four things instead:

1. **Know fast:** alerts that come from outside the box, so a compromised box cannot silence them.
2. **Limit the damage:** whatever the box holds can do little, and the box cannot reach the home network or the owner's other devices.
3. **Destroy fast:** every credential the box holds can be revoked from outside (from a phone). Then the box is wiped.
4. **Rebuild fast:** scripts plus backup produce the same box again.

Measures that only make an attack harder are out of scope unless they also serve one of the four. Examples: hiding keys from agents, credential proxies, egress allowlists, disk encryption, router configuration, remote power-off. If the box's Tailscale breaks, the box is rebuilt; there is no fallback access path.

## Decisions

In the scripts now:

- **Rebuildable by design:** the box can be moved, deleted or rebuilt at any time. A Multipass VM on the owner's computer is the test target for script changes. Changes land in the scripts and are applied by rerunning them, never by hand on the box.
- **Host and VM:** `setup-host.sh` (run once per host, safe to rerun) prepares an Ubuntu Server 24.04 host, amd64 or arm64, and builds a Multipass VM `orca` in which `setup-box.sh` runs. Inside the VM, Orca runs as a systemd user service for a non-root user with linger. The admin user keeps sudo on the host.
- **Hardening is a script, version-guarded:** the host script stops unless Ubuntu is 24.04, checks (never changes) the HWE kernel, grows the root LV into free space, masks sleep, makes sshd key-only (validated with `sshd -t`, refused if the admin has no key) and checks unattended-upgrades. `RUNBOOK.md` keeps only the interactive steps, the rationale and the porting notes; another Ubuntu release needs the script reviewed, not skipped.
- **VM sized to the whole machine:** CPUs default to the host's, memory to host RAM minus 2 GiB, disk to the root filesystem's size minus 60 GiB (`CPUS`, `MEM`, `DISK` override). These are chosen defaults, not measured needs. A VM is rebuilt, not resized.
- **Isolation:** two nftables tables of our own (`orca_isolation`, `orca_input`), loaded by `orca-fw.service`, never through `/etc/nftables.conf` (its default starts with `flush ruleset`). `orca_isolation` drops VM traffic to private and link-local ranges, to the host's connected LAN prefixes (read at load time) and to the host except DHCP and DNS. The unit is ordered before `snap.multipass.multipassd.service`, and a drop-in on multipassd requires it, so a failed load keeps the VM from starting. It has no `ExecStop`, so stopping it leaves the rules in place. The Multipass bridges are matched as `mpqemubr*` because several can exist.
- **Reach by proxy, not DNAT:** `systemd-socket-proxyd` units on the host listen on all addresses and forward Orca (6768) and the VM's SSH (2222) to the VM. DNAT would depend on Tailscale's `ts-forward` accept and on where Multipass's REJECT rules sit; the proxy needs only the host input table. The socket units are not `WantedBy=sockets.target`, because that made an ordering cycle with `orca-fw` (which waits for `network-online`) and systemd dropped them silently.
- **Host input table, LAN closed only after `--lock-lan`:** the first run leaves the LAN open, because the owner is on the LAN and Tailscale is not yet logged in. `--lock-lan`, run after SSH over the tailnet works, writes `/etc/orca-fw/lock-lan`; `orca-fw` then loads `orca_input` (tailscale0 only, replies, the bridge's DHCP/DNS) now and at every boot. There is no LAN backup path: recovery is a monitor and keyboard. The host's ufw is unused.
- **VM address pinned in the VM:** a static address (the bridge's subnet, host part 250, a chosen value) is added next to DHCP by a netplan file inside the VM. It needs no router change, and the proxies target it. Pure static breaks `multipass exec`, which finds the VM by its DHCP lease. The VM's own ufw admits SSH and Orca only from its gateway subnet, where the proxies connect from.
- **Multipass is held** (`snap refresh --hold`), because a refresh restarts the VM. Updating is a manual unhold, refresh, isolation check, hold (`RUNBOOK.md`).
- **Manual on purpose:** Tailscale login, signing the node under Tailnet Lock, disabling its key expiry, agent logins, Orca pairing. Each needs the owner's account or produces a credential.
- **What moves between boxes:** code moves through git, and agent memory and history through `backup.sh`/`restore.sh`. Logins and pairing are redone, not copied. Orca automations live in the server's sqlite profile state, which also holds other state, so `backup.sh` exports them with `orca-ide automations list --json` and `restore.sh` recreates them through the CLI (it has no import). Only automations that create a new worktree per run, for a repo cloned at its old path, are restored; others are reported and recreated by hand. Scheduled runs work headless: on a Multipass VM with Orca 1.4.245 (arm64), an automation fired from the service's own scheduler with no app open and survived a service restart; runs that launch an agent were not tested.
- **Where things live:** procedure and scripts in this repo; lessons and test results in the owner's wiki.

Agreed, not yet in the scripts (these replace the current behaviour):

- **Tailnet policy:** Tailscale ACLs let only the owner's devices reach the host's ports 22, 2222 and 6768, and let the box open no connections to other tailnet devices. Rebuilding the VM needs no Tailnet Lock signing, because Tailscale runs on the host.
- **GitHub identity:** a GitHub App installed on the owner's org. Its private key sits on the box readable by the runtime user, because a leak reaches only what the App may do. Permissions: contents and pull requests write, issues write if used, read on actions, checks and statuses. No administration, workflows, environments, secrets or member permissions.
- **Merge and deploy:** deploy credentials live in GitHub Actions environments, never on the box. The default branch deploys to a staging environment. Production deploys only from release tags. A tag ruleset lets only the owner create release tags, and production secrets are restricted to tag refs. A branch ruleset blocks force pushes and deletion of the default branch.
- **Agent accounts:** the box has its own email in the owner's Google Workspace and its own seat with each agent vendor, billed separately from the owner's personal accounts. Agents logged in as the owner pick up the owner's connectors (Gmail, Drive, Calendar). Logins are subscription-based only. No pay-per-use API keys, because their cost can't be capped for long-running work.
  - **Claude Code:** `claude setup-token` from the box's Claude Team seat. The token is model-only and does not load claude.ai connectors.
  - **Codex:** a Codex access token from the box's ChatGPT Business seat; the owner can revoke it from the workspace admin page. If access tokens are not available on Business, device-code login instead.
  - **Antigravity (`agy`) is not used.** Its FAQ says wrapping `agy` in third-party applications is not supported on consumer plans, and its terms call third-party access with Antigravity OAuth a breach. The remaining routes need an API key or Gemini Enterprise.
  - **GitHub Copilot CLI:** a Copilot Business seat for a GitHub user account of the box (separate from the GitHub App, which a Copilot seat can't use). It logs in with a fine-grained PAT that has only the Copilot Requests permission. A $0 budget for additional usage keeps the cost fixed.
- **Secrets:** the source of truth is 1Password. The box has a service account that can read only a box vault, holding only what the box needs. The revoke table and the owner's admin credentials live in a separate vault the box cannot read. When a project starts, the owner sets it up and gives the box only the credentials that project needs. Each one is dedicated to the box, has the narrowest scope, a spend cap and an expiry where the issuer supports them, and cannot mint other credentials.

## Open, by pillar

Rebuild (set up and rebuild):

- Base toolchain for any project, and the rule for recording each later addition in the scripts.
- Agent configuration: list what the owner's computer actually uses (settings, skills, plugins, MCP servers, Codex config), then take only that. Permission mode for unattended work.
- GitHub App token minting for `gh` and `git` (installation tokens last an hour).
- Agent accounts: create the box's Workspace email (own OU, unused services off), invite it to the Claude Team and ChatGPT Business workspaces, and check that Codex access tokens work on Business.
- Copilot CLI: check that a GitHub user account for the box can hold a Copilot Business seat, that a $0 budget blocks additional usage for that user, and how to install the CLI on amd64 and arm64.
- 1Password on the box: reading secrets without exceeding the Individual plan's 1,000 service-account reads per 24 hours.
- Phone and tablet clients: check that an Orca client exists and what it can do; Tailscale and pairing per device.
- The computer's new role: what it still needs, and what moves off it.
- Backup: what to back up, where it goes, how often, and a restore drill into a VM.
- Updates: bumping Orca and Codex now reruns the whole of `setup-box.sh` through the host script; whether that is acceptable for a routine bump.
- Whether `orca-ide serve service install` is safe to rerun.

Know fast:

- Alerts from outside the box: GitHub merges and deploys, spend at each provider, a dead-man check that fires when the box stops reporting.
- Health checks on the box: disk, Orca service.
- The alert channel to the owner's phone.

Limit damage:

- Verify that a tag ruleset can restrict release-tag creation to the owner.
- Verify whether a token without the workflows permission can merge a PR that changes workflow files.
- A per-project deploy template: build without secrets, deploy from a separate job that holds the environment's secrets.
- Write the Tailscale ACL policy.

Destroy:

- The revoke table: every credential the box holds and how to revoke it from a phone. A credential that cannot be revoked from outside does not go on the box. Claude: remove the box's member, or sign the box's account out of all sessions. Codex: revoke its access token in the workspace admin page. Copilot: revoke the PAT, or remove the box's Copilot seat. Whether removing a member stops a CLI login that is already running is undocumented for Claude and Codex, so the drill must test it.
- A revoke drill, run once from a phone against a test box.
- Update the retire procedure in `RUNBOOK.md` for the GitHub App, the 1Password service account and the host/VM split.

## What is tested

Verified on a disposable amd64 box:

- Fresh install of Ubuntu Server 24.04 with the HWE kernel and a one-time `apt full-upgrade`, then the committed `setup-host.sh` as written: it completed. The first Multipass call as root worked without extra authentication. The LV extend grew the root into the whole disk. The VM was created with the sized defaults, the SSH key reached it and the pinned address was applied.
- After `tailscale up` (login, Tailnet Lock signing, key expiry off), the host, the VM's SSH (proxied port) and the Orca port were reachable over the tailnet. `setup-host.sh --lock-lan` then closed the LAN: host SSH, the proxied SSH port and the Orca port were refused from the LAN and still reachable over the tailnet.
- From inside the VM, the LAN gateway (ping, TCP 80, TCP 53), the host's LAN address and the host's bridge address were blocked; the internet worked. Host SSH rejects password login.
- Orca pairing through the proxy worked and survived a reboot. After a clean reboot with the LAN closed, the host came back over the tailnet alone, with the firewall unit ordered before the Multipass daemon, the proxies, VM and Orca service back by themselves, and no systemd ordering cycle in the log.
- On the fresh install, with no monitor or keyboard attached, a hard power cut came back on its own: the host was reachable over the tailnet alone, the firewall, proxies, VM and Orca service were up, the LAN stayed closed, and the log again showed journal recovery messages.
- On an earlier install built partly by hand with the same units, a hard power cut came back on its own (firmware power-on after failure): the VM resumed and the firewall was in place. The log showed journal and boot-partition recovery messages, and the boot partition's FAT filesystem reported differences between boot sector and backup; boot succeeded.

Not tested:

- arm64.
- A LAN that uses public IPv4 or global IPv6 prefixes (only the private-range rules were exercised; the LAN prefix sets stayed empty or unused).
- A VM that gets a global IPv6 address.
- The agent logins, the GitHub login and pairing-URL secrecy steps of the runbook, beyond pairing.
- The boot-time loader once read an empty IPv4 LAN set because DHCP was not up yet (private ranges stayed covered).

## Known limits

- `setup-box.sh` pins the Orca and Codex versions; the installers it calls can change between uses. Rerun on a real box before trusting it.
- The service restart ends running agents; a reboot does too.
- Claude memory is keyed by repo path, so repos must be cloned to the same paths after a move.
- Isolation from the LAN holds only while the VM holds. An escape to the host reaches the home network.
- Code an attacker merges into the default branch reaches production when the owner next tags a release. Tagging is the point where the owner sees what the default branch holds.
